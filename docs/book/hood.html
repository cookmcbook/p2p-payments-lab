Under the hood

Spring, Hibernate, JPA and Docker do a lot of work you never typed. This section opens each one up, layer by layer, using output recorded from this project's running service. Nothing here is a paraphrase from memory: every log line, error message and number was captured from the real app.

You will be able to
  • name every process and layer that runs when you type docker compose up, and say what each one does;
  • explain what an does on its own (nothing) and who reads it;
  • describe how Spring builds your objects and passes them to each other, and read its startup errors;
  • explain why the AccountService you call is not the class you wrote;
  • say which of JPA, Hibernate, JDBC and HikariCP sends the SQL, and when;
  • predict which Docker build steps rerun after you change a file.

How to read this section. Each part starts with a short summary you can stop at. Below it, the panels, tracers and Under the hood boxes go deeper, one layer at a time. Take as much depth as you want. Later chapters link back here when they lean on an idea.

Everything that runs when you type docker compose up

Your Java code is the smallest part of the running system. It sits inside Spring, which sits inside a Java virtual machine, which runs inside a container, which runs inside a small Linux virtual machine that Docker Desktop manages on your computer. PostgreSQL runs in a second container beside it. Click a layer to see what it is and what it looked like on the machine that recorded this book.

The running system, outside in

Explorer · recorded
Your computer and Docker Desktop

Containers are a Linux feature. On Windows, Docker Desktop runs a small Linux virtual machine in the background, and every container is a process inside it. docker compose up reads compose.yaml and then, in order: builds the API image if needed, creates a private network, starts postgres, waits for its health check to pass, and only then starts payment-api.

$ docker compose ps
payment-api   Up 15 seconds
postgres      Up 21 seconds (healthy)

Docker Desktop is an apartment building. Each container is a flat with its own locked door, its own furniture (files) and its own doorbell (network address), but all flats share the building's foundations (the Linux kernel).

The Compose network

Compose creates one private network per project and runs a tiny DNS server on it. Every service gets a hostname equal to its service name. That is why DB_URL in compose.yaml says postgres:5432 and not localhost:5432: inside a container, localhost means that same container.

$ docker compose exec payment-api getent hosts postgres
172.18.0.2      postgres

$ docker network inspect p2p-payments-lab_default
p2p-payments-lab-payment-api-1 172.18.0.3/16
p2p-payments-lab-postgres-1 172.18.0.2/16

The line "8080:8080" under ports: forwards port 8080 on your computer into the container. That is the only reason curl localhost:8080 works from Windows. When the postgres container is stopped, its name leaves the DNS server. The API then fails with UnknownHostException: postgres, not "connection refused". See the startup tracer in Chapter 1.

The payment-api container

A is an ordinary Linux process with walls around it. It has its own view of the filesystem (unpacked from the ), its own network address and its own process list. It is not a virtual machine and has no kernel of its own. The files come from the base image eclipse-temurin:21-jre, which is built on Ubuntu.

$ docker compose exec payment-api id
uid=999(app) gid=999(app) groups=999(app)

$ docker compose exec payment-api cat /etc/os-release
PRETTY_NAME="Ubuntu 26.04.1 LTS"

$ docker compose exec payment-api sh -c "cat /proc/1/cmdline | tr '\0' ' '"
java -jar /app/app.jar

Two facts to keep. The process runs as user app, not root, because the Dockerfile says USER app. And Java is process 1: when process 1 exits, the container stops. A Spring startup failure therefore shows up in Compose as Exited (1).

The Java virtual machine

javac compiles .java files into : .class files containing instructions for an imaginary machine. The JVM is the program that runs that imaginary machine. It loads each class the first time something needs it, runs it, and compiles frequently used methods into real machine code while the program runs (just-in-time compilation).

INFO 1 --- [main] PaymentApiApplication : Starting PaymentApiApplication v0.1.0-SNAPSHOT
  using Java 21.0.12.1 with PID 1 (/app/app.jar started by app in /app)

Every log line names a in square brackets. [main] is the thread that runs startup. Requests run on other threads, as you'll see under Tomcat.

JarLauncher sets up a class loader that can read JARs nested inside a JAR, then calls our main. Notice the SQL files: migrations ship inside the JAR. That is how Flyway finds classpath:db/migration in a container that has no source code.

Tomcat

Tomcat is the web server, running inside the same JVM as a library. It owns the socket on port 8080 and a pool of worker (up to 200 by default). Each request is handled from start to finish by one thread, which is why every log line of one request carries the same thread name:

DEBUG [nio-8080-exec-5] DispatcherServlet : POST "/api/v1/accounts", parameters={}
DEBUG [nio-8080-exec-5] JpaTransactionManager : Creating new transaction …
INFO  [nio-8080-exec-5] AccountService : account opened accountId=4806a533-… currency=USD
DEBUG [nio-8080-exec-5] DispatcherServlet : Completed 201 CREATED

Startup logs show Tomcat twice. Tomcat initialized with port 8080 appears early, but the port isn't accepting connections yet. Tomcat started on port 8080 appears last, after every bean was created. If anything fails before that, the port never opens.

HikariCP, the connection pool

Opening a database connection takes a network handshake and a login. Doing that for every request would be slow, so opens connections at startup and lends them out. A transaction borrows one at BEGIN and returns it after COMMIT or ROLLBACK. The default pool holds 10.

INFO [main] HikariPool-1 - Starting...
INFO [main] HikariPool-1 - Added connection org.postgresql.jdbc.PgConnection@5f45bc8e
INFO [main] HikariPool-1 - Start completed.

postgres=# SELECT count(*), application_name, state FROM pg_stat_activity
           WHERE datname = 'p2p_lab' AND pid <> pg_backend_pid() GROUP BY 2, 3;
 count | application_name       | state
    10 | PostgreSQL JDBC Driver | idle

Ten idle connections, waiting. If an eleventh transaction starts while all ten are busy, it waits, for up to 30 seconds by default, and then fails. Chapter 3's concurrency work will make this visible.

Your code

Seventeen classes. They fall into two very different groups:

Beans (created once by Spring, shared by every request): AccountController, AccountService, JpaAccountRepository, AccountExceptionHandler, CapabilitiesController, TimeConfig and the Clock it makes. They hold no per-request data, which is why one object can serve many threads at once.

Values (created with new for each request and thrown away): Account, Money, CreateAccountRequest, AccountResponse, BalanceResponse, AccountBalance, AccountEntity. Most are records: immutable, so sharing them between threads is safe too.

Beans are the staff of a restaurant, hired once and serving every table. Values are the orders: written for one table, then discarded.

A completely separate process, in its own container, reached over the network. The API's JDBC driver talks to it over TCP port 5432 using PostgreSQL's own wire protocol.

The pgdata volume

A container's own files disappear when the container is removed. A volume is storage that Docker keeps separately and mounts into the container. compose.yaml mounts the pgdata volume at /var/lib/postgresql/data, where PostgreSQL keeps its files.

$ docker volume ls
p2p-payments-lab_pgdata

p2p_lab=# SELECT installed_rank, version, script, checksum, success FROM flyway_schema_history;
 1 | 1 | V1__baseline.sql |  1210165407 | t
 2 | 2 | V2__accounts.sql |  -830823360 | t

docker compose down removes the containers and keeps the volume, so your accounts survive. docker compose down -v deletes the volume too: every account and the Flyway history are gone, and the next start reruns V1 and V2 from scratch. The checksum column is how Flyway notices if someone edits an applied migration.

Just enough Java: annotations are labels

The single most useful fact for reading Spring code: an annotation does nothing by itself. @Transactional contains no transaction code. It is a label stored in the .class file. Something else has to look for the label at runtime, using , and act on it. When an annotation "doesn't work", the question is always: who was supposed to read it, and did they get the chance?

Annotation in this projectRead byWhenWhat the reader does
@SpringBootApplicationSpring BootStartupTurns on component scanning and auto-configuration
@RestController, @Service, @Repository, @ConfigurationSpring component scanStartup"Make one object of this class and manage it as a bean"
@BeanSpringStartupCalls the method once; its return value becomes a bean (our Clock)
@TransactionalSpring AOPStartup, then every callWraps the bean in a proxy that begins and ends transactions
@GetMapping, @PostMappingSpring MVCStartupBuilds the route table: method + path → Java method

A unit test runs new AccountService(repository, clock).open("Alice", Currency.USD). Does a transaction begin?

No. The test created the object with new, so Spring never saw it and never wrapped it in a proxy. The @Transactional label is still on the method, but nobody reads it. This is why AccountTest tests domain rules only, and why transaction behavior is checked in the integration test, where Spring builds the objects.

A few more Java words you'll meet. A class is a blueprint; an object is one thing built from it with new. An interface is a promise of methods with no body, such as AccountRepository; a class implements it. A record is a class whose fields are fixed at construction, with equals, hashCode and toString written for you. A constructor is the code that runs while an object is being built; records can add checks there, which is how Account rejects blank names.

Spring: a factory that builds and connects your objects

Your classes need each other: the controller needs the service, the service needs a repository and a clock, the repository needs Hibernate. Something has to create them in the right order and hand each one what it needs. Without Spring you would write that code yourself in main. With Spring, you declare what each class needs as constructor parameters, and Spring works out the order. This is called , and the thing doing it is the .

Here is roughly what Spring does for this project, written out by hand. This is a sketch for understanding, not real code:

// What Spring does at startup, written by hand (simplified sketch)
DataSource dataSource = new HikariDataSource(config);           // opens 10 connections
Flyway.configure().dataSource(dataSource).load().migrate();     // V1, V2
EntityManagerFactory emf = buildHibernate(dataSource);          // validates AccountEntity
Clock clock = new TimeConfig().clock();
AccountRepository repo = new JpaAccountRepository(sharedEntityManager(emf));
AccountService service = new AccountService(repo, clock);
AccountService proxy = wrapWithTransactions(service);           // the @Transactional part
AccountController controller = new AccountController(proxy);
tomcat.addRoutes(controller);
tomcat.start();                                                 // port 8080 opens last

    @Transactional: the object you call isn't the one you wrote
    
      
    When AccountController calls accountService.open(...), it isn't calling your AccountService. It is calling AccountService$$SpringCGLIB$$0, a subclass Spring generated at startup using a library called CGLIB. That subclass overrides every public method. The override begins a transaction, calls your real method, then commits if it returned normally or rolls back if it threw. That wrapper object is a .
    
      
    Sketched as Java (the real one is generated bytecode and never exists as source):
    
      
    // Sketch of the generated subclass, simplified
class AccountService$$SpringCGLIB$$0 extends AccountService {
    AccountService target;                 // your real object
    TransactionInterceptor tx;             // reads @Transactional

    @Override
    public Account open(String displayName, Currency currency) {
        var status = tx.begin("AccountService.open");  // borrow a connection, BEGIN
        try {
            Account result = target.open(displayName, currency);  // your code runs here
            tx.commit(status);                         // flush queued SQL, COMMIT
            return result;
        } catch (RuntimeException e) {
            tx.rollback(status);                       // ROLLBACK
            throw e;
        }
    }
}

      PostgreSQL: snapshots, row locks and the lock you didn't ask for
      
      
      Chapter 3's correctness rests on two PostgreSQL mechanisms. Neither appears in Java code, so here they are opened up.
      
      
      Snapshots (MVCC). PostgreSQL never overwrites a row in place. Every row version carries the id of the transaction that created it, and of the one that deleted or replaced it, if any. Each statement runs against a : a list of which transactions had committed when it started. A row version is visible only if its creator is in that committed list.
      
      
      That's why your uncommitted INSERT is invisible to everyone else, and why readers never wait for writers. Under , the default, the snapshot is retaken at the start of every statement. Two SELECTs in one transaction can see different data if someone committed in between. Chapter 3's lock-then-read relies on exactly that.
      
      
      Row locks. SELECT … FOR … doesn't change the row's data. It writes the locking transaction's id into the row's header, and a transaction that wants a conflicting lock waits for that transaction to end. There are four strengths, from strongest to weakest:
      
      
      
        
      Requested ↓ / Held →FOR UPDATEFOR NO KEY UPDATEFOR SHAREFOR KEY SHARE
      
        
          
      FOR UPDATE: "I may delete it or change its key"waitswaitswaitswaits
      
          
      FOR NO KEY UPDATE: "I may change it, but not its key". Our debit lock.waitswaitswaitsok
      
          
      FOR SHARE: "nobody may change it"waitswaitsokok
      
          
      FOR KEY SHARE: "nobody may delete it or change its key". Taken by every foreign key check.waitsokokok
      
              
      
      
      
      Read the bold cells together. Two debits of one account ask for NO KEY UPDATE twice, so the second waits. That's the queue we want. A posting that credits the account triggers a foreign key check, which asks for KEY SHARE, and that passes.
      
      
      With FOR UPDATE, the foreign key check would wait too. Chapter 3's deadlock tracer shows the cycle that results, with PostgreSQL's real error. Plain UPDATE statements take NO KEY UPDATE or UPDATE automatically, depending on whether they touch a key column.
      
      
      Seeing locks. While a transaction waits, its session appears in pg_stat_activity with wait_event_type = 'Lock', and pg_blocking_pids(pid) names the session it's waiting for. Recorded while psql held Alice's lock and the API tried to debit her:

      Delete @Configuration from TimeConfig and start the app. Which bean fails, and has Flyway already run?
      Parameter 1 of constructor in dev.p2plab.payments.account.application.AccountService required a bean of type 'java.time.Clock' that could not be found. Yes, Flyway and Hibernate both finished first, because they sit earlier in the dependency chain. Revert the change afterwards.
      
      
      Add a second @Repository class that implements AccountRepository. What happens?
      Startup fails: required a single bean, but 2 were found: inMemoryAccountRepository … jpaAccountRepository. Spring suggests @Primary or @Qualifier. Delete the class afterwards.
      
      
      With the debug overlay, create an account. In the log, does insert into account come before or after account opened?
      After. persist only queues the INSERT. Hibernate flushes at commit, which happens when open() has already returned and logged.
      
      
      With the debug overlay, request a balance. How many Creating new transaction lines appear?
      One, for balance. Its internal call to get(id) is self-invocation and bypasses the proxy, so get's @Transactional isn't consulted. Since Chapter 3 you'll also see Participating in existing transaction: the call to LedgerService.balance goes through that bean's proxy and joins the open transaction instead of starting a new one.
      
      
      Run docker compose stop postgres, then docker compose restart payment-api. What is the bottom-most Caused by?
      java.net.UnknownHostException: postgres. A stopped container's name disappears from the network's DNS, so the driver can't even find an address. Read Java cause chains from the bottom: that's the root cause. Start PostgreSQL again with docker compose start postgres.
      
      
      Run docker compose down, then up again. Are your accounts still there? And after down -v?
      After down: yes. The containers were removed, but the pgdata volume was kept. After down -v: no. The volume was deleted, and the next startup's Flyway log says it migrated the schema from scratch.

      What does the @Transactional annotation itself do when open() is called?
      
        
        
          
        • 
          
        • 
          
        • 
          
        • 
        
      
        
      Annotations are metadata. At startup Spring finds the label and wraps the bean in a generated subclass, and that subclass begins and ends transactions. Create the object with new and nothing happens.
      
      
      
      
      
        
      The bean list shows accountService with type AccountService$$SpringCGLIB$$0. What is that?
      
        
        
          
        • 
          
        • 
          
        • 
          
        • 
        
      
        
      It is a proxy: one object for the whole app, generated as bytecode by CGLIB. It overrides public methods, calls the transaction interceptor, then delegates to your real object.
      
      
      
      
      
        
      In the debug log of a create, when is insert into account sent to PostgreSQL?
      
        
        
          
        • 
          
        • 
          
        • 
          
        • 
        
      
        
      persist only adds the entity to the persistence context and queues the INSERT. The log shows committing, then the INSERT. That is also why a constraint violation surfaces at commit time.
      
      
      
      
      
        
      balance() calls get() in the same class. Both are @Transactional. How many transactions does the proxy start?
      
        
        
          
        • 
          
        • 
          
        • 
          
        • 
        
      
        
      Self-invocation bypasses the proxy. The recorded log has a single Creating new transaction … balance line and no line for get.
      
      
      
      
      
        
      Which layer actually sends SQL bytes to PostgreSQL?
      
        
        
          
        • 
          
        • 
          
        • 
          
        • 
        
      
        
      JPA is a specification with no implementation. Hibernate generates the SQL and hands it to JDBC. The driver speaks PostgreSQL's network protocol over a pooled connection. Flyway uses the same driver, but only at startup.

        • 
          
        • 
          
        • 
        
      
        
      Each container has its own network address. Compose puts both on one network and resolves service names; the recording shows postgres resolving to 172.18.0.2.
      
      
      
      
      
        
      You change one Java file and rebuild the image. Which slow step does the real Dockerfile skip?
      
        
        
          
        • 
          
        • 
          
        • 
          
        • 
        
      
        
      The cache only misses from the first changed step onward. Since COPY pom.xml and dependency:go-offline come before COPY src, they stay cached. The recording shows them as CACHED.

        • 
          
        • 
          
        • 
        
      
        
      Each layer wraps the error from the layer below. In the recorded PostgreSQL-stopped startup, the top says entityManagerFactory failed, and the bottom says UnknownHostException: postgres.
      
      
      
      
      
        
      Why can a single AccountController object safely serve many requests at the same time?
      
        
        
          
        • 
          
        • 
          
        • 
          
        • 
        
      
        
      Beans are singletons shared across Tomcat's worker threads. Per-request data lives in local variables and records. A mutable field on a bean would be a concurrency bug.
