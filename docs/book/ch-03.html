Chapter 3

A ledger that can't lose a cent, even under a crowd

Money can finally move. This chapter is about the two ways moving money goes wrong: a transfer that only half happens, and two transfers that each think they're the only one. You'll break both on purpose, then watch PostgreSQL stop them.

You will be able to
  • explain bookkeeping, and why "every entry sums to zero" means money is never created or destroyed;
  • say what guarantees and which line of code provides it;
  • reproduce a that overdraws an account, and explain why no single check catches it;
  • fix it with a , and say why the lock must come before the balance read;
  • explain a that the obvious lock causes, and the lock mode that avoids it;
  • describe what happens when 1,000 requests arrive at once: where they queue, and what limits throughput.

How to read this chapter. Each section starts with the idea in a few sentences. The tracers, the playground and the Under the hood boxes go deeper. Every log line, error and number was recorded from this project's running service on 30 October 2026, or from its tests; most are abridged (timestamps and package names shortened), and the captions say so.

New to backend work? Start here: six ideas this chapter builds on

Each idea below has three parts: what it is, why this chapter needs it, and where you'll see it. Every tracer step in this chapter uses the same pattern, with the full technical detail one click further down.

1 · A request runs on a thread

What: when a program calls our API, the web server (Tomcat, built into the app) hands that request to one worker thread. A thread is one independent line of work: it runs our Java code for that request from start to finish.

Why: the server has up to 200 threads, so up to 200 requests run at the same time. That's why two transfers from the same account can overlap.

Where: the thread's name is in every log line, like [nio-8080-exec-7]. Two different names means two requests running side by side.

2 · A transaction is all-or-nothing

What: a groups several database changes. It starts with BEGIN. It ends with either COMMIT, which saves everything at once, or ROLLBACK, which throws everything away.

Why: a transfer writes three rows. If the app crashed halfway, a transaction guarantees that none of them count, so money can't half-move.

Where: @Transactional on LedgerService.transfer. Spring begins the transaction before the method runs. It commits when the method returns normally, and rolls back if the method throws an exception.

3 · Unsaved changes are invisible to others

What: until a transaction commits, its new rows can be seen only by itself. PostgreSQL's default rule, called READ COMMITTED, is that each SQL statement sees everything that was committed before that statement started.

Why: this is how two transfers can both see Alice's $10.00. Neither can see the other's debit, because neither has committed yet.

Where: the race playground. Watch the "uncommitted −$10.00" that the other transaction can't see.

4 · A lock makes others wait their turn

What: a is a claim on one database row. Another transaction that asks for a conflicting lock on that row waits until the first transaction ends. Locks are released automatically at COMMIT or ROLLBACK.

Why: it turns "at the same time" into "one after the other" for exactly the thing that mustn't overlap: decisions about one account's money.

Where: SELECT … FOR NO KEY UPDATE on the paying account's row, in JpaLedgerRepository.lockForDebit.

5 · An exception means "stop and refuse"

What: Java code refuses by throwing an exception: an object describing the problem. The method stops at that line, and the exception travels up to whichever code called it, until something catches it.

Why: when an exception leaves a @Transactional method, Spring rolls the transaction back. Then an exception handler turns it into an HTTP answer for the client.

Where: InsufficientFundsException becomes 409 Conflict in LedgerExceptionHandler. Step through the Overdraft scenario in the tracer.

6 · HTTP status codes summarize the outcome

What: every HTTP answer starts with a three-digit code. 2xx means success, 4xx means the request was refused, 5xx means the server failed.

Why: programs, and retries, act on the code before reading anything else. "Refused, don't retry" (400) is a different message from "refused, might work later" (409).

Where: this chapter uses 201 Created, 400 Bad Request, 404 Not Found and 409 Conflict.

Mental model: money moves, it never appears

Picture a jar of marbles for every account. A transfer takes marbles out of one jar and puts the same number in another. If you count every marble in every jar, the total never changes. That's the whole idea of bookkeeping, used by accountants for 500 years.

In this project each movement is a made of two or more . A posting is a signed amount for one account: negative takes money out, positive puts it in. The rule that makes it double-entry: the postings of an entry always add up to zero.

Journal entryPostingAccountamount_minor
FUNDING (Alice gets $10.00)1Simulated funding source-1000
2Alice+1000
TRANSFER (Alice pays Bob $3.00)1Alice-300
2Bob+300

Alice's balance is the sum of her postings: 1000 - 300 = 700. Nothing stores "700"; it's computed every time, exactly as Chapter 2 promised.

So where did Alice's first $10.00 come from? From the , a special account seeded by the migration. It's the only account allowed to go negative. Its balance is minus the total money ever issued, so the sum over the entire ledger is always exactly zero. That gives you a one-line audit. This is real output from the lab database after every experiment in this chapter:

p2p_lab=# SELECT SUM(amount_minor) AS whole_ledger, count(*) AS postings FROM posting;
 whole_ledger | postings
--------------+----------
            0 |     3322
Under the hood: how signed amounts map to "debit" and "credit"

Accounting textbooks don't use signs. They write every amount as positive in one of two columns, or , and the rule is "total debits = total credits".

Which column increases a balance depends on the kind of account. That's why "credit" means "money in" on your bank statement, while the bank's own books call the same event a credit to a liability: the bank owes you more.

This project uses one signed column instead: negative for money out of an account, positive for money in, from the account holder's point of view. "Debits equal credits" becomes SUM(amount_minor) = 0, which a database can check in one query. In this book and in the code, a debit is a negative posting and a credit is a positive one. ADR 0005 records the trade-off.

Atomicity: both postings, or neither

A transfer writes three rows: the entry and two postings. Suppose the app crashed after writing Alice's -300 but before Bob's +300. Three dollars would vanish.

is the guarantee that this can't happen. All the writes in one become visible together at COMMIT, or none of them do. PostgreSQL provides it: until COMMIT, the new rows exist only for the transaction that wrote them, and if the connection dies first, PostgreSQL throws them away.

In Java it's the same @Transactional you met in Chapter 2. LedgerService.transfer is one transaction: the checks, the entry and both postings commit together, or roll back together.

The rules are enforced twice, the same defense in depth as Chapter 2:

    The race: two transfers, one balance
    
      
    The rule "a customer can't spend money they don't have" sounds like one if: read the balance, and insert the debit only if it's enough. That pattern is called , and on its own it is broken.
    
      
    Alice has $10.00. Two requests to send $10.00 arrive at the same moment, on two Tomcat threads, as two transactions. Both read the balance before either has committed. Both see $10.00, both checks pass, both commit. Alice ends at −$10.00.
    
      
    No database constraint can stop this. Each entry is balanced, each posting is valid, and nothing is wrong with either transaction on its own. The bug lives only in how the two overlap.

        The fix: lock first, then read
        
      
        The fix is to make debits of one account take turns. Before reading Alice's balance, the transaction locks Alice's account row with SELECT … FOR NO KEY UPDATE. A second transaction that wants to debit Alice blocks at that line until the first commits.
        
      
        When it wakes up, its balance read runs after the first one's commit. In READ COMMITTED each statement gets a fresh view, so it sees the new balance and refuses correctly.
        
      
        Three details make this correct, and each was found by a test:
        
      
          
        
        1. Order matters: lock, then read. If you read first and lock second, you are back to the race.
          2. 
        
        2. Only debits lock. A credit can only increase a balance. If a debit reads a balance that is missing a just-committed credit, the worst outcome is a refusal the customer could retry. So Bob's account is never locked when he receives money, and parallel payments to one account don't queue.
          3. 
        
        3. A fixed order when several accounts are debited. Accounts are visited sorted by id, so two entries can't each hold one lock while waiting for the other's.
          4.

          What 1,000 requests at once look like
          
      
          infra/lab/race.mjs opens two accounts, funds one, then sends every transfer at the same instant and checks the invariants afterwards. Here's a real run with 1,000 one-cent transfers from a $5.00 balance:
          
      
          $ node infra/lab/race.mjs --requests 1000 --amount 1 --fund 500
Sending 1000 A→B transfers of $0.01 at once. A starts with $5.00.
Status codes: 201 × 500, 409 × 500
Latency ms: min 425, median 1439, p95 1640, max 1660
Throughput: 587 requests/s over 1705 ms
Connection pool (9 samples): at most 10 connections in use, at most 189 requests waiting for one
Balances: A $0.00, B $5.00, A + B $5.00
Invariants hold: no negative balance, and no money created or destroyed.
          
      
          Exactly 500 succeeded: that's how many cents there were. The answer is always correct; the cost of being correct shows up as waiting. A request passes through three queues, each narrower than the last:
          
      
          
        
          QueueWidthWho waits thereSeen in the run
          
        
          
          Tomcat worker threads200 (Spring Boot's default)Requests whose connection has been accepted but no thread is freeAbout 800 of the 1,000 at the peak
          
          
          HikariCP 10Threads that are running but need a database connection189 waiting, 10 in use: 189 + 10 ≈ 200 threads
          
          
          Alice's row lock1Transactions that hold a connection but are waiting for another debit of Alice to commitUp to 9 of the 10 connections
          
                  
      
          
      
          The narrowest queue sets the speed. Here it's the single row lock: Alice is a , and every debit of her commits one after another. Debits of different accounts don't share that queue, so 1,000 transfers spread over 1,000 senders would finish far faster. They'd be limited by the 10 connections instead. Measuring and raising those limits is Chapter 8.
          
      
          Under the hood: why the median request took 1.4 seconds when each transfer takes a few milliseconds
          
        
          A single uncontended transfer took 46–57 ms end to end in smaller runs, almost all of it HTTP and JSON. Its time inside the database is a few milliseconds.
          
        
          With 1,000 arriving together, a request's  is mostly waiting: in Tomcat's accept queue, then for a connection, then for the lock. The first requests through finish quickly. The last wait for everything ahead of them.
          
        
          That's why the minimum (425 ms) and the maximum (1,660 ms) are so far apart, while  stays roughly flat at about 500–900 requests per second across runs. Adding requests adds waiting, not work per second.
          
        
          A note on measurement: the pool sampler's own requests queue behind the burst too. In short runs it sometimes lands only before and after the burst and reports zero, which is why the script prints how many samples it took.

          Exercises
          
      
          Run race.mjs with the defaults ($10.00, 100 transfers of $1.00). How many 201s and how many 409s?
          Exactly 10 and 90, every time. There were ten dollars. The recorded runs printed 201 × 10, 409 × 90. If you ever see 11, the lock is broken.
          
      
          In LedgerService.post, swap the two lines so the balance is read before lockForDebit. Which test fails, and how?
          fiftySimultaneousDebitsNeverOverdraw, usually with more than 10 completed and a negative balance for Alice. Every transaction reads $10.00 first, then queues for the lock with a stale number in hand. aWaitingDebitReadsTheBalanceCommittedWhileItWaited fails too. Revert afterwards.
          
      
          Change FOR NO KEY UPDATE to FOR UPDATE and run mvn verify. What happens?
          oppositeDirectionTransfersDoNotDeadlock errors with ERROR: deadlock detected (SQLSTATE 40P01), while locking tuple … in relation "account". The other tests still pass. That is why the deadlock needed its own test. This exact change was run while writing the chapter.
          
      
          In psql, hold Alice's lock (BEGIN; SELECT … FOR NO KEY UPDATE;) and, in another terminal, send a transfer to Alice. Does it wait?
          No. Credits don't take the debit lock, and the foreign key's FOR KEY SHARE doesn't conflict with FOR NO KEY UPDATE, so the transfer returns 201 immediately. Now send a transfer from Alice: that one waits until you COMMIT.
          
      
          Fund Alice with $10.00, then run SELECT SUM(amount_minor) FROM posting WHERE account_id = '00000000-0000-0000-0000-00000000f00d';. What's the sign, and why?
          Negative, and exactly minus the total of every funding entry ever posted. The funding account is where simulated money enters the ledger. Its negative balance is the other half of every customer's positive one, which is why the whole ledger sums to zero.
          
      
          Exercise 6: stop a stalled transaction blocking everyone
          Today a transaction that holds Alice's lock and stalls blocks every other debit of Alice indefinitely, as the psql experiment showed (4.2 s for a 6 s sleep).
          Make waiting fail fast instead. Run SET LOCAL lock_timeout = '2s' at the start of the transaction, or set it per connection with HikariCP's connection-init-sql. Then map the resulting SQLSTATE 55P03 (lock_not_available) to a 503 with a Retry-After header.
          Repeat the psql experiment and expect the curl to fail after about 2 s. Decide whether a timed-out transfer is safe to retry. Hint: did anything commit?
          
      
          Exercise 7: a reversal
          Postings can never be edited. Add EntryKind.REVERSAL and a LedgerService.reverse(entryId) that posts the opposite of an existing entry: same accounts, amounts negated.
          Which balance checks still apply? (A reversal debits the original recipient, who may have spent the money.) You'll need a new migration to allow the new kind in the CHECK constraint. Why can't you edit V3__ledger.sql instead?

          If every entry is zero, any sum of entries is zero. Funding doesn't break this: it's an ordinary entry, with −X to the funding account and +X to the customer.
          
      
          
      
          
        
          The app crashes after Hibernate sends Alice's -300 posting but before Bob's +300. What does the database contain afterwards?
          
        
            
          
            •

            •

          Recorded in the test: both reads returned 1000, both commits succeeded, and Alice ended at −1000. Rules about a single row or entry can't see two transactions together.
          
      
          
      
          
        
          A developer moves ledger.balance(...) to before ledger.lockForDebit(...). Is the lock still useful?
          
        
            
          
            • 
          
            • 
          
            • 
          
            • 
        
          
        
          READ COMMITTED gives each statement a fresh view, but a value you already read doesn't change. Only a read that runs after the lock is granted sees the previous debit's commit.
          
      
          
      
          
        
          Why does a transfer to Bob not lock Bob's account?
          
        
            
          
            • 
          
            • 
          
            • 
          
            • 
        
          
        
          The rule being protected is about debits. A debit that reads a balance missing a simultaneous credit errs on the safe side: it refuses money that was arriving.
          
      
          
      
          
        
          With FOR UPDATE, transfers A→B and B→A deadlocked. Why?
          
        
            
          
            • 
          
            • 
          
            • 
          
            • 
        
          
        
          The lock you didn't write, the foreign key's, completed the cycle. FOR NO KEY UPDATE is compatible with FOR KEY SHARE but still conflicts with itself, so debits still queue and foreign key checks pass through.
          
      
          
      
          
        
          How does PostgreSQL resolve a deadlock?
          
        
            
          
            • 
          
            • 
          
            • 
          
            • 
        
          
        
          The aborted transaction is rolled back, so nothing is half-written. But the user sees a failure, which is why the lock mode was changed to avoid the cycle altogether.

            • 
          
            •
