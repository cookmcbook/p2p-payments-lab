Your Java code is the smallest part of the running system. It sits inside Spring, which sits inside a Java virtual machine, which runs inside a container, which runs inside a small Linux virtual machine that Docker Desktop manages on your computer. Your computer and Docker Desktop

Containers are a Linux feature. On Windows, Docker Desktop runs a small Linux virtual machine in the background, and every container is a process inside it. docker compose up reads compose.yaml and then, in order: builds the API image if needed, creates a private network, starts postgres, waits for its health check to pass, and only then starts payment-api.

$ docker compose ps
payment-api   Up 15 seconds
postgres      Up 21 seconds (healthy)

Docker Desktop is an apartment building. Each container is a flat with its own locked door, its own furniture (files) and its own doorbell (network address), but all flats share the building's foundations (the Linux kernel).

The Compose network

Compose creates one private network per project and runs a tiny DNS server on it. Every service gets a hostname equal to its service name. That is why DB_URL in compose.yaml says postgres:5432 and not localhost:5432: inside a container, localhost means that same container.

$ docker compose exec payment-api getent hosts postgres
172.18.0.2      postgres

$ docker network inspect p2p-payments-lab_default
p2p-payments-lab-payment-api-1 172.18.0.3/16
p2p-payments-lab-postgres-1 172.18.0.2/16

The line "8080:8080" under ports: forwards port 8080 on your computer into the container. That is the only reason curl localhost:8080 works from Windows. When the postgres container is stopped, its name leaves the DNS server. The API then fails with UnknownHostException: postgres, not "connection refused". See the startup tracer in Chapter 1.

It loads each class the first time something needs it, runs it, and compiles frequently used methods into real machine code while the program runs (just-in-time compilation).

Tomcat

Tomcat is the web server, running inside the same JVM as a library. It owns the socket on port 8080 and a pool of worker (up to 200 by default). Each request is handled from start to finish by one thread, which is why every log line of one request carries the same thread name:

DEBUG [nio-8080-exec-5] DispatcherServlet : POST "/api/v1/accounts", parameters={}
DEBUG [nio-8080-exec-5] JpaTransactionManager : Creating new transaction …
INFO  [nio-8080-exec-5] AccountService : account opened accountId=4806a533-… currency=USD
DEBUG [nio-8080-exec-5] DispatcherServlet : Completed 201 CREATED

Startup logs show Tomcat twice. Tomcat initialized with port 8080 appears early, but the port isn't accepting connections yet. Tomcat started on port 8080 appears last, after every bean was created. If anything fails before that, the port never opens.

HikariCP, the connection pool

Opening a database connection takes a network handshake and a login. Doing that for every request would be slow, so opens connections at startup and lends them out. A transaction borrows one at BEGIN and returns it after COMMIT or ROLLBACK. The default pool holds 10.

INFO [main] HikariPool-1 - Starting...
INFO [main] HikariPool-1 - Added connection org.postgresql.jdbc.PgConnection@5f45bc8e
INFO [main] HikariPool-1 - Start completed.

postgres=# SELECT count(*), application_name, state FROM pg_stat_activity

    10 | PostgreSQL JDBC Driver | idle

Ten idle connections, waiting. If an eleventh transaction starts while all ten are busy, it waits, for up to 30 seconds by default, and then fails. Chapter 3's concurrency work will make this visible.

Your code

Seventeen classes. They fall into two very different groups:

Beans (created once by Spring, shared by every request): AccountController, AccountService, JpaAccountRepository, AccountExceptionHandler, CapabilitiesController, TimeConfig and the Clock it makes. They hold no per-request data, which is why one object can serve many threads at once.

Values (created with new for each request and thrown away): Account, Money, CreateAccountRequest, AccountResponse, BalanceResponse, AccountBalance, AccountEntity. Most are records: immutable, so sharing them between threads is safe too.

Beans are the staff of a restaurant, hired once and serving every table. Values are the orders: written for one table, then discarded.

Just enough Java: annotations are labels

The single most useful fact for reading Spring code: an annotation does nothing by itself. @Transactional contains no transaction code. It is a label stored in the .class file. Something else has to look for the label at runtime, using , and act on it. When an annotation "doesn't work", the question is always: who was supposed to read it, and did they get the chance?

A unit test runs new AccountService(repository, clock).open("Alice", Currency.USD). Does a transaction begin?

No. The test created the object with new, so Spring never saw it and never wrapped it in a proxy. The @Transactional label is still on the method, but nobody reads it. This is why AccountTest tests domain rules only, and why transaction behavior is checked in the integration test, where Spring builds the objects.

A few more Java words you'll meet. A class is a blueprint; an object is one thing built from it with new. An interface is a promise of methods with no body, such as AccountRepository; a class implements it. A record is a class whose fields are fixed at construction, with equals, hashCode and toString written for you. A constructor is the code that runs while an object is being built; records can add checks there, which is how Account rejects blank names.

Spring: a factory that builds and connects your objects

Your classes need each other: the controller needs the service, the service needs a repository and a clock, the repository needs Hibernate. Something has to create them in the right order and hand each one what it needs. Without Spring you would write that code yourself in main. With Spring, you declare what each class needs as constructor parameters, and Spring works out the order. This is called , and the thing doing it is the .

Here is roughly what Spring does for this project, written out by hand. This is a sketch for understanding, not real code:

    TransactionInterceptor tx;             // reads @Transactional

    @Override

        }

      PostgreSQL: snapshots, row locks and the lock you didn't ask for
      
      
      Chapter 3's correctness rests on two PostgreSQL mechanisms. Neither appears in Java code, so here they are opened up.
      
      
      Snapshots (MVCC). PostgreSQL never overwrites a row in place. Every row version carries the id of the transaction that created it, and of the one that deleted or replaced it, if any. Each statement runs against a : a list of which transactions had committed when it started. A row version is visible only if its creator is in that committed list.
      
      
      That's why your uncommitted INSERT is invisible to everyone else, and why readers never wait for writers. Under , the default, the snapshot is retaken at the start of every statement. Two SELECTs in one transaction can see different data if someone committed in between. Chapter 3's lock-then-read relies on exactly that.
      
      
      Row locks. SELECT … FOR … doesn't change the row's data. It writes the locking transaction's id into the row's header, and a transaction that wants a conflicting lock waits for that transaction to end. There are four strengths, from strongest to weakest:
      
      
      
        
      Requested ↓ / Held →FOR UPDATEFOR NO KEY UPDATEFOR SHAREFOR KEY SHARE
      
        
          
      FOR UPDATE: "I may delete it or change its key"waitswaitswaitswaits
      
          
      FOR NO KEY UPDATE: "I may change it, but not its key". Our debit lock.waitswaitswaitsok
      
          
      FOR SHARE: "nobody may change it"waitswaitsokok
      
          
      FOR KEY SHARE: "nobody may delete it or change its key". Taken by every foreign key check.waitsokokok
      
              
      
      
      
      Read the bold cells together. Two debits of one account ask for NO KEY UPDATE twice, so the second waits. That's the queue we want. A posting that credits the account triggers a foreign key check, which asks for KEY SHARE, and that passes.
      
      
      With FOR UPDATE, the foreign key check would wait too. Chapter 3's deadlock tracer shows the cycle that results, with PostgreSQL's real error. Plain UPDATE statements take NO KEY UPDATE or UPDATE automatically, depending on whether they touch a key column.
      
      
      Seeing locks. While a transaction waits, its session appears in pg_stat_activity with wait_event_type = 'Lock', and pg_blocking_pids(pid) names the session it's waiting for. Recorded while psql held Alice's lock and the API tried to debit her:

            Mental model: money moves, it never appears
            
      
            Picture a jar of marbles for every account. A transfer takes marbles out of one jar and puts the same number in another. If you count every marble in every jar, the total never changes. That's the whole idea of  bookkeeping, used by accountants for 500 years.

            Under the hood: how signed amounts map to "debit" and "credit"
            
        
            Accounting textbooks don't use signs. They write every amount as positive in one of two columns,  or , and the rule is "total debits = total credits".
            
        
            Which column increases a balance depends on the kind of account. That's why "credit" means "money in" on your bank statement, while the bank's own books call the same event a credit to a liability: the bank owes you more.
            
        
            This project uses one signed column instead: negative for money out of an account, positive for money in, from the account holder's point of view. "Debits equal credits" becomes SUM(amount_minor) = 0, which a database can check in one query. In this book and in the code, a debit is a negative posting and a credit is a positive one. ADR 0005 records the trade-off.
            
      
            

      
            Atomicity: both postings, or neither

              The race: two transfers, one balance
              
      
              The rule "a customer can't spend money they don't have" sounds like one if: read the balance, and insert the debit only if it's enough. That pattern is called , and on its own it is broken.
              
      
              Alice has $10.00. Two requests to send $10.00 arrive at the same moment, on two Tomcat threads, as two transactions. Both read the balance before either has committed. Both see $10.00, both checks pass, both commit. Alice ends at −$10.00.
              
      
              No database constraint can stop this. Each entry is balanced, each posting is valid, and nothing is wrong with either transaction on its own. The bug lives only in how the two overlap.

                  The fix: lock first, then read
                  
      
                  The fix is to make debits of one account take turns. Before reading Alice's balance, the transaction locks Alice's account row with SELECT … FOR NO KEY UPDATE. A second transaction that wants to debit Alice blocks at that line until the first commits.
                  
      
                  When it wakes up, its balance read runs after the first one's commit. In READ COMMITTED each statement gets a fresh view, so it sees the new balance and refuses correctly.
                  
      
                  Three details make this correct, and each was found by a test:
                  
      
                    
        
                  1. Order matters: lock, then read. If you read first and lock second, you are back to the race.
                    2. 
        
                  2. Only debits lock. A credit can only increase a balance. If a debit reads a balance that is missing a just-committed credit, the worst outcome is a refusal the customer could retry. So Bob's account is never locked when he receives money, and parallel payments to one account don't queue.
                    3. 
        
                  3. A fixed order when several accounts are debited. Accounts are visited sorted by id, so two entries can't each hold one lock while waiting for the other's.
                    4.

                    Glossary
                    
      
                    Every underlined term in the book links here. Definitions describe how this project uses the word.
                    
      
                    
        
                    Atomicity
                    
        
                    The "A" in ACID: all of a transaction's writes become visible together at COMMIT, or none do. A transfer's two postings can never be half-written.
                    
        
                    Annotation
                    
        
                    A label in Java source, such as @Transactional, stored in the compiled class. It does nothing on its own; a framework or the compiler reads it and acts. See Under the hood.
                    
        
                    Auto-configuration
                    
        
                    Spring Boot's conditional setup: configuration classes that apply only when their conditions hold, usually "this library is on the classpath". It is why adding Flyway to pom.xml was enough to make migrations run.
                    
        
                    Available balance
                    
        
                    What can be spent right now: the ledger balance minus holds, which are funds reserved for payments still in flight. Holds arrive with payments in Chapter 4.
                    
        
                    Bean
                    
        
                    An object created and managed by the Spring container, normally one per application (a singleton) and shared by every request. At Chapter 2 this app had 372, of which 8 came from our code. At Chapter 3, with the lab profile, it has 378, of which 11 are ours.
                    
        
                    Bean Validation
                    
        
                    The Jakarta standard for declaring input rules with annotations such as @NotBlank and @Size. Spring checks them when a parameter is marked @Valid.
                    
        
                    Connection pool
                    
        
                    A set of database connections opened in advance and lent out per transaction, because opening one per request is slow. This project uses HikariCP with its default of 10.
                    
        
                    Check-then-act
                    
        
                    Reading a value, deciding, then writing based on what was read ("if the balance is enough, insert the debit"). Unsafe under concurrency unless something stops the value changing between the check and the act.
                    
        
                    Container
                    
        
                    A Linux process started from an image and isolated from others: its own filesystem view, network address and process list. It shares the host's kernel, which makes it much lighter than a virtual machine.
                    
        
                    Contract test
                    
        
                    A test of an interface's promises (status codes, field names, validation) with the code behind it replaced by a mock. Fast, but blind to the real implementation.
                    
        
                    Deadlock
                    
        
                    Two or more transactions each waiting for a lock another one holds, so none can proceed. PostgreSQL detects the cycle after deadlock_timeout (1 s) and aborts one with SQLSTATE 40P01.
                    
        
                    Debit and credit
                    
        
                    The two sides of a double-entry movement. In this project a debit is a negative posting (money leaves the account) and a credit a positive one (money arrives). Accounting textbooks use unsigned columns instead.
                    
        
                    Deferred constraint
                    
        
                    A constraint or constraint trigger declared DEFERRABLE INITIALLY DEFERRED, so it is checked at COMMIT instead of after each statement. Needed when a rule spans several rows inserted one at a time.
                    
        
                    Dependency injection
                    
        
                    Classes receive their collaborators through the constructor instead of creating them. Spring builds the objects and passes them in, which makes swapping a fake in tests easy.
                    
        
                    Double-entry bookkeeping
                    
        
                    Recording every movement as postings that sum to zero: what leaves one account arrives in another. If every entry balances, the whole ledger always sums to zero, and money can't be created or destroyed by accident.
                    
        
                    Fat JAR
                    
        
                    A JAR that contains the application's classes and every library it needs, so java -jar app.jar runs with nothing else installed except Java. Spring Boot's is started by its own JarLauncher.
                    
        
                    Flush
                    
        
                    The moment Hibernate turns its queue of pending changes into SQL and sends it to the database. Normally just before commit, and before any query that could see the pending changes.
                    
        
                    Flyway
                    
        
                    A tool that applies versioned SQL migration files in order and records each one in the flyway_schema_history table.
                    
        
                    Funding account
                    
        
                    The single seeded account (…f00d, kind FUNDING) that simulated money comes from. It may go negative; its balance is minus the total ever issued.
                    
        
                    Hibernate
                    
        
                    The JPA implementation this project uses: an ORM (object-relational mapper) that tracks entity objects, generates SQL for them, and turns result rows back into objects.
                    
        
                    Hot account
                    
        
                    An account so many transactions debit at once that its row lock becomes the bottleneck: debits of it commit strictly one at a time. The funding account and popular merchants are typical examples.
                    
        
                    Idempotency
                    
        
                    The property that doing something twice has the same effect as doing it once. Payment APIs achieve it with a client-supplied key, so a retried request returns the original result instead of paying twice.
                    
        
                    Image
                    
        
                    A read-only template for containers: a stack of filesystem layers plus settings such as the user and the start command. Built from a Dockerfile.
                    
        
                    IoC container
                    
        
                    "Inversion of control": instead of your code creating its collaborators, a container creates them and passes them in. In Spring, the container is the application context, and the objects are beans.
                    
        
                    Isolation level (READ COMMITTED)
                    
        
                    How much concurrent transactions can see of each other. PostgreSQL's default, READ COMMITTED, gives each statement a fresh snapshot of committed data, so two reads in one transaction can differ. Stricter levels are REPEATABLE READ and SERIALIZABLE.
                    
        
                    JDBC
                    
        
                    Java's built-in low-level database API (Connection, PreparedStatement, ResultSet). Each database ships a driver that implements it. Hibernate and Flyway use it; our code doesn't.
                    
        
                    Journal entry
                    
        
                    One atomic ledger movement: a group of two or more postings that sum to zero, stored in journal_entry. Kinds today: FUNDING and TRANSFER. Never edited; a mistake is undone with a reversing entry.
                    
        
                    JPA
                    
        
                    Jakarta Persistence: a specification of interfaces and annotations (EntityManager, @Entity) for storing Java objects in relational databases. It contains no implementation; Hibernate provides one.
                    
        
                    JVM and bytecode
                    
        
                    The Java Virtual Machine runs bytecode: the instructions in .class files that javac produces. It loads classes on demand and compiles hot code to machine code while running.
                    
        
                    Latency
                    
        
                    How long one request takes, from sending to receiving the answer. Under load it is mostly time spent waiting in queues, not doing work.
                    
        
                    Layer (Docker)
                    
        
                    One slice of an image's filesystem, produced by one Dockerfile instruction. Layers are cached and shared, so an unchanged step is reused on the next build.
                    
        
                    Ledger balance
                    
        
                    The sum of all postings to an account. Computed, never typed in.
                    
        
                    Migration
                    
        
                    A versioned SQL script that changes the database schema. Once applied, it is never edited; the next change is a new, higher version.
                    
        
                    Minor unit
                    
        
                    The smallest unit of a currency. For USD it is the cent, so $12.34 is 1234 minor units.
                    
        
                    Multi-stage build
                    
        
                    A Dockerfile with several FROM lines. Early stages build; the final stage copies only the result, leaving compilers and source code behind.
                    
        
                    MVCC and snapshots
                    
        
                    Multi-version concurrency control: PostgreSQL keeps old row versions and tags each with the transaction that wrote it. A statement reads a snapshot (the set of transactions committed when it started), so readers never wait for writers and uncommitted rows stay invisible.
                    
        
                    Persistence context
                    
        
                    Hibernate's per-transaction memory: every entity it is tracking, keyed by id, plus a queue of SQL still to send. persist adds to it; flush empties the queue into the database.
                    
        
                    Port and adapter
                    
        
                    A port is an interface the core of the application defines, such as AccountRepository. An adapter implements it with a specific technology, such as JpaAccountRepository with JPA.
                    
        
                    Posting
                    
        
                    One line of a journal entry: a signed amount for one account, stored in posting. Negative takes money out, positive puts it in. Postings are immutable, and an account's balance is the sum of its postings.
                    
        
                    Profile (Spring)
                    
        
                    A named switch, such as lab, activated with SPRING_PROFILES_ACTIVE. Beans marked @Profile("lab") are created only when it is active; otherwise they don't exist at all.
                    
        
                    Problem Detail
                    
        
                    The standard JSON error format from RFC 9457, with type, title, status, detail and instance fields, served as application/problem+json.
                    
        
                    Proxy
                    
        
                    An object that stands in for another and adds behavior around its method calls. Spring's AccountService$$SpringCGLIB$$0 is a generated subclass that wraps each call in a transaction.
                    
        
                    Race condition
                    
        
                    A bug whose outcome depends on the timing of concurrent operations. It passes when requests arrive one at a time and fails only when they overlap, which is why it needs dedicated concurrency tests.
                    
        
                    Read model
                    
        
                    Data computed for display from authoritative records, rather than being authoritative itself.
                    
        
                    Reflection
                    
        
                    Java's ability to inspect classes while the program runs: list their methods, read their annotations, call their constructors. It is how frameworks act on annotations they've never seen your code use.
                    
        
                    Row lock
                    
        
                    A lock on one table row, taken with SELECT … FOR UPDATE (or NO KEY UPDATE, SHARE, KEY SHARE) and held until the transaction ends. A conflicting request waits. It doesn't change the data and never blocks plain reads.
                    
        
                    Testcontainers
                    
        
                    A library that starts real dependencies, such as PostgreSQL, in throwaway Docker containers for the length of a test run.
                    
        
                    Thread
                    
        
                    One independent path of execution inside a process. Startup runs on main; Tomcat handles each request on one of its worker threads, named like nio-8080-exec-5 in the logs.
                    
        
                    Throughput
                    
        
                    How many requests complete per second. Limited by the narrowest queue a request must pass through, such as a hot account's row lock or the 10-connection pool.
                    
        
                    Transaction
                    
        
                    A unit of database work that either fully commits or fully rolls back. Partial results are never visible.
                    
        
                    Trigger
                    
        
                    A function the database runs automatically on INSERT, UPDATE, DELETE or TRUNCATE. Because it runs inside PostgreSQL, no client (Java, psql, a script) can skip it.
