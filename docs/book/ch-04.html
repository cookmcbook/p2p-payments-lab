Chapter 4

A payment you can safely send twice

The internet loses answers. A phone sends "pay Bob $3.00", the server does it, and the reply never arrives. This chapter builds the payment API so that the phone can simply ask again, and get the same payment back instead of paying twice.

  • name the five states, the moves allowed between them, and which state means "reconcile, don't retry";

  • say how an and a turn a retry into a , even for 20 retries at once;
  • state the and what it costs a client who retries too late;
  • explain why the payment runs as three transactions, in a separate bean.

New to backend work? Start here: five ideas this chapter builds on

Each idea below has three parts: what it is, why this chapter needs it, and where you'll see it. Chapter 3's primer covers threads, transactions, locks and exceptions.

1 · A timeout tells you nothing

What: a timeout is a client giving up on waiting for an answer. It doesn't stop the server. The server may still be working, and may finish.

Why: after a timeout the client can't tell "the payment never happened" from "it happened and the answer got lost". Retrying blindly can pay twice; not retrying can leave the user unsure.

Where: the Client times out scenario in the tracer, recorded with a client that gave up after 2 s while the server finished 0.7 s later.

2 · Idempotent means "twice is the same as once"

What: an operation is if repeating it changes nothing further. Pressing a lift's call button twice is idempotent; ordering a pizza twice is not.

Why: making "pay" idempotent makes retrying safe, which is the only cure for a lost answer.

Where: the Idempotency-Key header on POST /api/v1/payments, and the idempotency_key table.

3 · A state machine is a list of allowed moves

What: a state machine is a fixed set of states and the moves allowed between them. Anything not on the list is refused.

Why: a payment that jumps from "accepted" straight to "completed", or comes back to life after "rejected", is a bug that can move money wrongly. Listing the allowed moves makes such bugs throw instead.

Where: PaymentStatus.canMoveTo, and the database CHECKs in V4__payments.sql.

4 · A hash is a fingerprint of some data

What: a hash such as SHA-256 turns any text into a fixed-length string (64 hex characters). The same text always gives the same hash; a tiny change gives a completely different one.

Why: to check that a retry asks for the same payment, the server compares the hash of the new request with the one it stored the first time.

Where: RequestFingerprint.of.

5 · HTTP 201, 202 and 422

What: 201 Created: a new resource exists. 202 Accepted: the request was taken but isn't finished. 422 Unprocessable Content: the request is well formed but can't be done as asked.

Why: clients act on the code first. Here, 201 means "this payment is final, read its status", 202 means "ask again with the same key", and 422 means "you reused a key for something else".

Where: PaymentController and PaymentExceptionHandler.

Mental model: a payment is a record with a state

In Chapter 3, a transfer either happened (201) or didn't (409), and nothing remembered asking. That's fine inside one database transaction, and hopeless across a network. A payment is different: it is a row in the payment table, created when the request arrives, with a that only moves forward.

StatusIn plain wordsMoneyFinal?
ACCEPTEDRecorded, and the payer's money is reservedHeld, not movedNo
PROCESSINGWe've started moving itHeld, not movedNo
COMPLETEDDone: the journal entry is postedMovedYes
REJECTEDRefused, with a reason (here: INSUFFICIENT_FUNDS)Never heldYes
INDETERMINATEWe asked a bank and don't know if it moved the moneyUnknownNo, but never retried automatically

The allowed moves are ACCEPTED → PROCESSING → COMPLETED; PROCESSING → INDETERMINATE; and INDETERMINATE → COMPLETED | REJECTED, by only. No Chapter 4 code reaches INDETERMINATE. Moving money inside our own ledger is one database transaction, and its outcome is never unknown. It is defined and tested now so that Chapter 7, which calls a (mock) bank, slots into the same shape.

Holds: money that's spoken for

Between "accepted" and "completed", the payer's money must not be spendable by anything else. A reserves it: a row in ledger_hold that lowers the available balance and leaves the ledger balance alone. Capturing the hold posts the real journal entry.

after step 1 only (ACCEPTED, $6.00 held of $10.00):
{"accountId":"…alice","currency":"USD","ledgerMinor":1000,"availableMinor":400}
after COMPLETED ($3.00 payment):
{"accountId":"…alice","currency":"USD","ledgerMinor":700,"availableMinor":700}

The first line is asserted by PaymentIntegrationTest.aHoldLowersAvailableButNotLedger…; the second was recorded from the running service. Ids shortened.

A hold spends available money, so it has exactly Chapter 3's problem. The fix is the same: placeHold locks the account row with FOR NO KEY UPDATE before it reads the available balance. And every debit now checks available, not ledger, so a direct transfer can't spend held money either. Both rules have tests that fail if you remove them; both were removed on purpose while writing this chapter.

Idempotency keys: the client names the payment

The client invents a key, such as rent-2026-11, sends it as Idempotency-Key, and sends the same key on every retry. The server stores (payer, key) → fingerprint, payment:

ArrivesServer answersRecorded
New keyDoes the work; stores key + payment201, Idempotent-Replayed: false, COMPLETED
Same key, same payee, amount and currencyThe original payment, unchanged201, Idempotent-Replayed: true, same id
Same key, $4.00 instead of $3.00Refuses; stores nothing422, "Idempotency-Key was already used for a different request"
Same key, different payerA separate payment: keys are scoped to the payerTested in keysAreScopedToThePayer
No keyRefuses400, "Required header 'Idempotency-Key' is not present."
Same key, 25 hours laterA new payment: the key expiredTested in anExpiredKeyMayBeReusedForANewPayment

The last row is the : a key means one payment for 24 hours, then may be reused. An hourly job deletes expired keys; payments are never deleted. Insufficient funds is a stored REJECTED payment with 201, not an error. That keeps a key's answer stable: if Alice is refused, gets paid, and retries with the same key, she gets the same refusal. A new attempt needs a new key.

Under the hood: what is actually inside the fingerprint?

SHA-256("v1|" + payeeAccountId + "|" + amountMinor + "|" + currency), as 64 lowercase hex characters, stored in request_fingerprint CHAR(64). It's built from the parsed Java values, so {"amountMinor":300,"currency":"USD",…} and the same fields in a different order, or with extra spaces, give the same fingerprint.

The payer isn't in it because the payer is already half of the primary key. The v1 is a version: if a future chapter adds a field (a memo, say), it switches to v2, and old fingerprints can never accidentally equal new ones.

    Exercises
    
      
    Send the same payment three times with one key. How many journal entries are posted, and what differs between the three responses?
    One entry. All three responses are 201 with the same id and body; only Idempotent-Replayed differs: false, then true, true.
    
      
    Pay $50.00 from $10.00 with key k. Fund the payer with $100.00 and retry with k. What comes back?
    The same REJECTED payment, Idempotent-Replayed: true. A key's answer never changes. A new attempt needs a new key, and that one succeeds. Tested in aReplayedRejectionStaysRejectedEvenAfterThePayerIsFunded.
    
      
    Run race.mjs --requests 100 (100 different keys, $1.00 each, from $10.00). How many of each status?
    COMPLETED × 10, REJECTED × 90, and every HTTP status is 201. In Chapter 3 the same run gave 201 × 10, 409 × 90; now refusals are stored payments.
    
      
    In psql, lock your latest payment row (BEGIN; SELECT … FROM payment … FOR UPDATE;, no commit). Does a new payment wait? Does a replay of the locked one?
    Neither waits (recorded: 60 ms and 10 ms). The new payment locks only its own row. The replay finds a COMPLETED payment, which is final, so pay never reaches steps 2 and 3, the only steps that lock the payment.
    
      
    Exercise 5: make placeHold throw InsufficientFundsException instead of returning empty, and have accept catch it and build the REJECTED payment. Run insufficientFundsIsAStoredRejectionAndMovesNothing. What happens?
    It fails: expected: 201 CREATED but was: 500 INTERNAL_SERVER_ERROR. The exception passed through placeHold's proxy, which marked the shared transaction rollback-only. accept caught the exception and carried on, but its commit then failed with UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only. Nothing is stored: not the rejection, not the key. Recorded while writing this chapter. Revert afterwards.
    
      
    Exercise 6: make POST /api/v1/accounts idempotent
    Today a retried account creation opens a second account. What would the key be scoped to, when no payer exists yet? Which fields go into the fingerprint? Is a 24-hour retention right for this endpoint?
    
      
    Exercise 7: a sweeper for stuck holds
    Add a @Scheduled job that moves payments stuck in ACCEPTED for more than 10 minutes to REJECTED and releases their holds (status = 'RELEASED'). You'll need a new RejectionReason, a transition ACCEPTED → REJECTED and a migration. Why is this safe for ACCEPTED, and why would it be dangerous for a future PROCESSING payment that has called a bank?
