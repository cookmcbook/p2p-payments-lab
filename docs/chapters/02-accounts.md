# Chapter 2 — Accounts, persistence, and a balance that cannot lie

> **Reading this after Chapter 3?** This chapter describes the code as it was at Chapter 2: `AccountService.balance` returned zero. [Chapter 3](03-ledger.md) replaced it with a sum over ledger postings.

## Learning objectives

By the end of this chapter you can:

- explain why a balance should be *derived* from records rather than stored as an editable number;
- represent money without floating point;
- trace an HTTP request through controller → service → domain → repository → database and say which layer owns which rule;
- write a Flyway migration whose constraints defend invariants even when application code is bypassed;
- distinguish unit, contract and integration tests, and know what each one can and cannot prove;
- run an integration test against a real PostgreSQL with Testcontainers.

## Terminology

- **Account** — a named container that will hold funds. In this chapter it holds none.
- **Minor unit** — the smallest unit of a currency. For USD it is the cent; $12.34 is `1234` minor units.
- **Ledger balance** — the sum of everything that has been posted (finalized) to an account.
- **Available balance** — what can be spent right now: the ledger balance minus *holds* (funds reserved for in-flight payments). Holds arrive with payments.
- **Posting / journal entry** — an immutable record that moves an amount between accounts. Introduced in Chapter 3.
- **Read model** — data computed for display from authoritative records, rather than being authoritative itself.
- **Port and adapter** — a *port* is an interface the core of the application defines (`AccountRepository`); an *adapter* implements it with a specific technology (`JpaAccountRepository` with JPA).
- **Transaction** — a unit of database work that either fully commits or fully rolls back.
- **Migration** — a versioned, ordered, never-edited SQL script that evolves the schema. Flyway records applied versions in `flyway_schema_history`.
- **Problem Detail** — the standard JSON error format from RFC 9457 (`type`, `title`, `status`, `detail`, `instance`), served as `application/problem+json`.
- **Testcontainers** — a library that starts real dependencies (here PostgreSQL) in throwaway Docker containers during tests.

## Conceptual model

A bank account statement is not a single number someone types in; it is a list of entries, and the balance at the bottom is their sum. If the number and the list ever disagree, the list wins. This chapter adopts that rule *before* there is a list:

```
account (who)            postings (what happened)        balance (read model)
──────────────           ────────────────────────        ────────────────────
id, name, currency  ◄──  Chapter 3                  ──►  SUM(postings) = 0 today
```

Because no postings exist, every balance is exactly zero, and there is intentionally **no endpoint, column or field that can set a balance**. That is the strongest possible form of "transfers never create funds": there is no code that could.

The account itself is deliberately small: an id generated by the server, a display name, a currency, and a creation time.

## Design tradeoffs

| Decision | Chosen | Alternative | Why |
| --- | --- | --- | --- |
| Money type | `long` minor units ([ADR 0002](../adr/0002-money-and-balance-representation.md)) | `BigDecimal` scale 2 | No fractional cents by construction; simple JSON integers |
| Balance storage | None — derived | `balance` column | One source of truth; nothing can drift |
| Funding before ledger | Impossible | "Seed balance" on create | A seed creates money from nothing |
| Id generation | Server-side random UUID | DB sequence; client-supplied | Not guessable/enumerable like 1, 2, 3; no DB round trip to obtain it |
| Listing accounts | No endpoint | `GET /accounts` | Without authentication (Chapter 5), a list exposes everyone |
| Persistence API | `EntityManager.persist` behind a port | Spring Data `JpaRepository` | Spring Data's `save()` on an entity with a pre-assigned id calls `merge`, which issues a `SELECT` first; `persist` is one `INSERT` and is explicit |
| Validation | API (`@Valid`) **and** domain **and** DB `CHECK` | One layer | Defense in depth: each layer protects against callers that bypass the one above |
| Schema ownership | Flyway + `ddl-auto: validate` | Hibernate `update` | Schema changes are reviewed, versioned SQL; Hibernate only checks the mapping |

## Annotated code path

Paths are relative to `apps/payment-api/src/main/java/dev/p2plab/payments/`.

1. **`account/api/CreateAccountRequest.java`** — `@NotBlank @Size(max = 80)` and `@Pattern(regexp = "USD")`. These run *before* the controller method; on failure Spring returns 400 and the service is never invoked.
2. **`account/api/AccountController.java`** — three methods, each one line of translation. `ResponseEntity.created(uri)` sets `201` and the `Location` header, telling the client where the new resource lives.
3. **`account/application/AccountService.java`** — `@Transactional` on `open` means the `INSERT` commits when the method returns or rolls back if it throws. `readOnly = true` on reads lets the driver and Hibernate skip dirty checking. The log line includes the id and currency, not the display name.
4. **`account/domain/Account.java`** — a Java `record` whose compact constructor enforces invariants. Every `Account` instance that exists is valid, whether it came from an HTTP request or from the database. `open(...)` truncates the clock to microseconds — see the failure laboratory for why.
5. **`account/domain/AccountRepository.java`** — the port. The domain package has zero Spring/JPA imports, so `AccountTest` runs in milliseconds.
6. **`account/persistence/JpaAccountRepository.java` and `AccountEntity.java`** — package-private; nothing outside `persistence` can reach JPA types. The entity converts to and from the domain record.
7. **`resources/db/migration/V2__accounts.sql`** — the `CHECK` constraints mirror the domain rules. Note what is *absent*: a balance column.
8. **`account/application/AccountService.balance`** — returns `Money.zero(currency)` for both balances, with a comment pointing at Chapter 3.

## Request walkthrough

```http
POST /api/v1/accounts
Content-Type: application/json

{"displayName": "  Alice Example ", "currency": "USD"}
```

1. Tomcat accepts the connection; Spring's `DispatcherServlet` matches `POST /api/v1/accounts` to `AccountController.open`.
2. Jackson converts the body to `CreateAccountRequest`. Bean Validation passes (the name is not blank, ≤ 80 chars; currency is `USD`).
3. `AccountService.open` begins a transaction. `Account.open` generates a UUID, strips the name to `"Alice Example"`, and reads the injected `Clock`.
4. `JpaAccountRepository.add` calls `entityManager.persist`. At commit, Hibernate flushes `INSERT INTO account (...)`. PostgreSQL evaluates the `CHECK` constraints.
5. The service logs `account opened accountId=… currency=USD`.
6. The controller returns:

```http
HTTP/1.1 201 Created
Location: /api/v1/accounts/a0ef351c-aaea-424f-88c8-15969f76c7c3

{"id":"a0ef351c-…","displayName":"Alice Example","currency":"USD","createdAt":"2026-10-29T04:25:51.846024Z"}
```

Then `GET /api/v1/accounts/{id}/balance` returns `{"accountId":"…","currency":"USD","ledgerMinor":0,"availableMinor":0}`.

## Failure scenarios

| Scenario | What happens | Where it is handled |
| --- | --- | --- |
| `currency: "EUR"` | 400 problem JSON | `@Pattern` on `CreateAccountRequest` |
| Blank or 81-character name | 400 | `@NotBlank`/`@Size`; domain would also reject |
| Malformed JSON | 400 | Jackson / Spring MVC |
| `GET /api/v1/accounts/not-a-uuid` | 400 | Path variable type conversion |
| Unknown but well-formed id | 404 `{"title":"Account not found"}` | `AccountExceptionHandler` |
| Someone inserts `EUR` directly in SQL | `ERROR: new row violates check constraint` | `V2__accounts.sql` |
| Database down at startup | App fails to start (Flyway cannot connect) | Chapter 1 failure lab |
| Client retries a POST after a timeout | **A second account is created.** | Not handled yet — idempotency keys are Chapter 4 |
| Schema and entity disagree (e.g. you rename a column only in SQL) | App refuses to start: `Schema-validation: missing column` | `ddl-auto: validate` |

## Failure laboratory: the microsecond bug

While building this chapter, the integration test failed:

```
expected: AccountResponse[..., createdAt=2026-10-29T04:22:46.720618319Z]
 but was: AccountResponse[..., createdAt=2026-10-29T04:22:46.720618Z]
```

The `POST` response echoed the in-memory `Instant` (nanoseconds, from the JVM clock), but PostgreSQL `TIMESTAMPTZ` stores microseconds, so the subsequent `GET` returned a different value. A client comparing the two — or using `createdAt` as a cursor — would see the record "change". The `@WebMvcTest` could not catch this because it never touches a database; only the real-database test did.

The fix lives in the domain (`Account.open` truncates to `ChronoUnit.MICROS`) and is pinned by `AccountTest.truncatesCreationTimeToDatabasePrecision`. Lesson: the value you return on write must be the value you will return on read.

## Exercises (with expected observations)

1. **Predict, then observe validation.** POST `{"displayName":"Bob","currency":"usd"}`. *Expect* 400 — the pattern is case-sensitive. Decide whether the API should normalize case; if so, where (DTO, controller, or domain) and why.
2. **Defense in depth.** With the stack running, `docker compose exec postgres psql -U p2p_lab -d p2p_lab` and run `INSERT INTO account VALUES (gen_random_uuid(), 'Mallory', 'EUR', now());`. *Expect* a `check constraint` violation. Explain why the API's `@Pattern` alone would not have stopped this.
3. **Break the mapping.** Change `@Column(name = "display_name")` in `AccountEntity` to `"name"` and run `mvn verify`. *Expect* the integration test to fail at context startup with a schema-validation error, while `AccountControllerTest` still passes. Explain which test levels can detect which bugs. Revert.
4. **Never edit an applied migration.** Add a comment line to `V2__accounts.sql` and restart the Compose stack (which keeps its volume). *Expect* startup to fail with a Flyway checksum mismatch. Explain why Flyway refuses, then revert. (How would you legitimately add a column? → `V3__….sql`.)
5. **Observe non-idempotency.** POST the same body twice. *Expect* two different ids. Write down how a client could have ended up sending it twice; keep this note for Chapter 4.
6. **Log hygiene.** `docker compose logs payment-api | grep "account opened"`. *Expect* the id and currency but no display name.
7. **Close the tab gap.** In psql, `INSERT INTO account VALUES (gen_random_uuid(), E'\t', 'USD', now());` *succeeds*: `btrim()` removes only spaces, so a tab-only name passes the `CHECK`, even though Bean Validation and `String.isBlank()` both reject it. Write `V3__account_display_name_not_whitespace.sql` that drops `account_display_name_check` and adds a check rejecting any all-whitespace name (hint: `display_name ~ '\S'`). Add an integration test that inserts `E'\t'` and expects `DataIntegrityViolationException`. Consider what happens if an existing row already violates the new rule.

## Review questions

1. Why does the `account` table have no `balance` column, and what would go wrong if a later feature added one and updated it independently of postings?
2. `0.1 + 0.2` in `double` is `0.30000000000000004`. Show how `long` minor units avoid this, and name one thing `long` cannot do that `BigDecimal` can.
3. Validation exists in the DTO, the domain record, and the database. Which of these would still protect you if a future batch job wrote accounts directly with JDBC?
4. Why is `JpaAccountRepository` package-private, and what does that prevent?
5. Why does the API return 404 rather than 403 for an unknown account, and how might that answer change once accounts have owners (Chapter 5)?
6. What can `AccountControllerTest` prove that `AccountPersistenceIntegrationTest` cannot, and vice versa? Use the microsecond bug as an example.
7. Why is there no `GET /api/v1/accounts` list endpoint?
